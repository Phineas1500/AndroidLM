# The engine under memory tagging (MTE) (2026-10-08)

GrapheneOS runs apps on its hardened allocator with the Pixel 8's memory tagging (MTE), which
stops a process at the first heap access outside its allocation. Our native engine had never run
under it, so a latent out-of-bounds read there would crash the app on GrapheneOS and nowhere else.
Checked on the stock Pixel 8 Pro without wiping it.

- **Turning MTE on:** `adb shell setprop arm64.memtag.bootctl memtag-once` (the property the
  Developer options switch sets; `ro.arm64.memtag.bootctl_supported=1` on this phone), then a
  reboot. With `memtag-once` the next boot after that is untagged again.
- **Tagging a native program:** `MEMTAG_OPTIONS=sync` in its environment. A probe that reads one
  granule past a 32-byte allocation (`work/memtest/mte_probe.c`) runs normally without it and dies
  with `SIGSEGV, code 9 (SEGV_MTESERR)` with it, so the switch works.
- **The engine:** the 1.5.0 engine (`bmoe-lazy`), heap tagging in sync mode. It ran the usual
  request (a 1,216-token research prompt and two 300-token drafts) on the 12GB settings (5,000 MiB
  cache, 1,280-token prompt reading, pinned dense weights) and on the 8GB settings (1,500 MiB,
  512, unpinned). There were no faults, nothing in the crash log, and the generated text was
  identical to the untagged runs (same MD5 across all three).

| Run | Load | Prompt | Writing |
|---|---|---|---|
| MTE, 12GB settings | 9.7 s | 34.5 s | 5.2 tokens/s |
| MTE, 8GB settings | 11.2 s | 63.2 s | 3.8 tokens/s |

This covers scudo's tagging (stock Android), not GrapheneOS's own allocator, and the engine, not
the app's other native libraries (SQLite, zstd), which run in the app process. Those would need a
build with `android:memtagMode="sync"`, or GrapheneOS itself.

## The whole app (2026-10-09)

A test build of 1.7.0 with `android:memtagMode="sync"` on the application (heap tagging for the
app process, where SQLite, zstd and the research pipeline run) and `MEMTAG_OPTIONS=sync` for the
engine it starts, on a boot with memory tagging on (the probe died with `SEGV_MTESERR`, "Buffer
Overflow, 16 bytes right of a 32-byte allocation"). Eight questions, covering every route: sources
first from Wikipedia (the full-text build), the Ethereum library and Wikivoyage, the places route
(vegan restaurants in Lisbon), answer first with the source check ("Why is the sky blue?"), and a
follow-up that rewrites the question first ("And why are sunsets red?"). All completed, writing
at 3.6-4.6 tokens/s, and the crash log stayed empty.

A release build does not let adb read the app process's memory maps, so the app's tagging is
inferred from the manifest and the boot state rather than seen. GrapheneOS's own allocator is
still untested.
