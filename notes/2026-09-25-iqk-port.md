# ik_llama.cpp's expert kernels in the engine (2026-09-25)

`notes/2026-09-25-prefill-kernels.md` measured ik_llama.cpp reading this model's prompts 2.1x faster
than mainline llama.cpp on the same ARM cores, from its batched matrix kernels for the experts'
IQ2_XS and IQ3_XXS weights. This note ports those kernels into the engine's llama.cpp fork and
measures them on the VM and the phone. Result: the 1,216-token research prompt is read in 37 s
instead of 73 s on the Pixel 8 Pro, short prompts are no slower, generation is unchanged, and the
outputs differ from the old kernels only as much as any rounding-level change does. In the app,
a sources-first question now finishes in a median 100 s instead of 148 s (first words at 62 s
instead of 111 s), with answers graded the same.

## The port (patches/llama.cpp/0001-ggml-cpu-iqk-moe-kernels.patch)

The engine's `ggml_compute_forward_mul_mat_id` computes each expert one weight row and one token
at a time (`vec_dot`), decoding the 2- and 3-bit weights again for every token. The patch adds
`ggml/src/ggml-cpu/iqk-moe.cpp` (about 550 lines of ik's aarch64 code, MIT, notice kept) and calls
it for an expert once the expert-ready hook has returned, when the weights are IQ2_XS or IQ3_XXS
and the expert has 2 or more tokens. The expert's rows are handed out to the threads in 32-row
chunks through mul_mat_id's own per-expert counter, and for each chunk:

- fewer than 32 tokens: each weight row is decoded once and multiplied by up to 8 tokens at a
  time (ik's `mul_mat_qX_K_q8_K_T` with its IQ2_XS/IQ3_XXS dequantizers);
- 32 tokens or more: the rows are converted to ik's 8-row interleaved 8-bit layout (Q8_K_R8) and
  multiplied with `vdotq_laneq_s32` (ik's `mul_mat_q8_k_r8_q8_k`).

Everything else is unchanged: the activations are the Q8_K rows mul_mat_id already builds (ik's
Q8_K block has an extra field, but these kernels read only the scale and the quants), and the row
mapping and output layout are mul_mat_id's own. Generation (one token per expert) never takes the
new path. `GGML_IQK_MOE=0` turns the port off at run time; `GGML_IQK_MOE_MIN_ROWS`,
`GGML_IQK_MOE_CONVERT_MIN_ROWS` and `GGML_IQK_MOE_CHUNK_ROWS` move the thresholds and the chunk.
The dense Q5_K/Q6_K weights stay on llama.cpp's repacked kernels (patches/0006). Other targets
compile a stub, so the fork still builds everywhere.

`scripts/build-android-engine.sh` now applies `patches/llama.cpp/*.patch` inside
`third_party/llama.cpp`, and recognises an already-patched tree by reverse-applying each series
in a scratch copy (the old one-patch-at-a-time check failed on stacked patches that edit the
same file, so re-running the script on a built tree stopped with "patch does not apply").

## Correctness

**Kernel test** (`ggml/src/ggml-cpu/test-iqk-moe.cpp` in the patch; VM, Neoverse-N1): random
weight bits, random activations, row lengths 512 and 2048, 2-100 tokens, rows claimed in 16-row
chunks in a shuffled order, the down projection's row mapping (slot modulo, strided output).
Against a double-precision reference:

| Path | Largest error, relative to the output RMS | RMS error |
|---|---|---|
| llama.cpp's `vec_dot` | 2-6e-7 | |
| port, under 32 tokens | 2-6e-7 (the same, up to float rounding) | 5-8e-8 |
| port, 32 tokens or more | 2.4-4.9e-2 | 5.8-6.7e-3 |

From 32 tokens the weights are re-quantized to 8 bits per 256-weight block before the multiply;
that is ik's design, and random weights are its worst case (every sub-block scale from 1 to 31).

**Whole model** (`llama-perplexity`, 16 chunks of 512 tokens of Wikipedia text, the same binary
with the port off and on, KL divergence of the next-token distributions against the port off):

| | Perplexity vs port off | Mean KLD | Same top token |
|---|---|---|---|
| port off, run twice | identical | 0.000000 | 100% |
| port, under-32 path only (exact up to rounding) | +0.21% ± 0.23% | 0.0082 | 96.2% |
| port, both paths (the default) | +0.30% ± 0.25% | 0.0088 | 95.8% |

The engine is deterministic run to run, but any rounding-level change moves this model's outputs
by about 0.008 KLD: 256 experts with 8 chosen per token, and a recurrent state that carries a
flipped choice forward. The 8-bit path adds at most 0.0006 on top of that floor, and neither
perplexity change is outside its error bar. Chunking the rows changes nothing numerically (each
output is computed the same way whichever thread computes it).

## Speed on the Pixel 8 Pro

Engine CLI with the app's flags (5 threads on cpus 4-8, repacked dense weights, 5000 MiB expert
cache), each run from 30.5 C, configurations in mirrored order. The research-sized prompt is 1,216
tokens with 200 written; the short one is 110 tokens ("Why does the Dead Sea...") with 200 written.

**Research prompt:**

| Kernels | Read lanes | Slices | Prompt read | Flash read |
|---|---|---|---|---|
| old | 2 | 512 | 72.55, 72.70 s | 22.1 GB |
| port, rows split evenly | 2 | 512 | 48.25, 48.09, 48.13, 47.96, 48.31, 48.25 s | 22.1 GB |
| port, rows in chunks | 2 | 512 | 45.66, 45.45 s | 22.1 GB |
| port, rows in chunks | 4 | 512 | 46.52, 46.10 s | 22.1 GB |
| port, rows split evenly | 2 | 1,280 | 38.31, 38.09 s | 9.0 GB |
| port, rows in chunks | 2 | 1,280 | 36.74, 36.57 s | 9.0 GB |
| port, rows in chunks | 4 | 1,280 | 36.92, 37.00 s | 9.0 GB |

Handing out rows in chunks rather than in equal shares lets the X3, the fastest of the five
cores, take more of them (CPU time 204 s instead of 221 s). Reading the prompt in one slice
streams the experts from flash once instead of three times.

**Short prompt, and why 4 read lanes:**

| Kernels | Read lanes | Prompt read | Mean clock, A715 / X3, while reading | Compute cores busy |
|---|---|---|---|---|
| old | 2 | 6.86, 7.21, 6.89, 6.95, 7.01, 7.00 s | 2176 / 2705 MHz, 2137 / 2716 | 93% |
| port, rows split evenly | 2 | 10.54, 10.74 s | | |
| port, rows in chunks | 2 | 10.19, 9.85, 10.04, 10.03 s | 1780 / 1958 MHz, 1683 / 2006 | 71-72% |
| port, rows in chunks | 4 | 6.51 s | 2024 / 2478 MHz | 82% |
| old | 4 | 6.56 s | 2216 / 2892 MHz | 96% |

A short prompt still streams most experts (5.5 GB here), so it waits on flash. With the old
kernels the compute cores stayed busy enough to hold their clocks; with the port they finish
early and sleep, the governor (sched_pixel) lowers their clocks, and the engine's two read lanes,
which run on those same cores, read slower (5.5 GB in 9.5 s instead of 7.3 s). The prompt took
longer than with the old kernels. Four lanes keep enough reads in flight: the port then reads
the short prompt in 6.5 s, as fast as the old kernels with four lanes and faster than the old
default. On the research prompt four lanes cost about 1% (46.3 against 45.6 s at 512, 37.0 against
36.7 s at 1,280).

**Generation** is untouched by the port (tokens/s after the short prompt, 200 written): old
kernels 6.90-7.03 with 2 lanes and 7.15 with 4; port 7.00-7.23 with 2 lanes and 7.22 with 4.
After the research prompt it measured 6.0-6.2 tok/s at 1,280-token slices against 5.5-5.7 at 512;
the port does not run during generation, so that is probably less heat left from a shorter prompt
read (and the cache holding a different set of experts after one slice), not the kernels.

**Memory.** The compute buffer llama.cpp reserves for the widest slice is 502 MiB at 512 tokens
and 1,256 MiB at 1,280 (`llama-perplexity -lv 4`, same model and context). The runs above showed
no more swapping at 1,280 than at 512 (peak engine swap 84 MiB in both, apart from one run at
251 MiB).

## What the app uses

- the engine built with the patch (the port is on unless `GGML_IQK_MOE=0`);
- `ioThreads` 4 instead of 2 for every phone (`AppSettings`);
- `--ubatch 1280` on phones with 11 GiB or more of total memory (the same test as the 5000 MiB
  cache default), 512 elsewhere (`AppSettings.defaultUbatch`). The app's research prompts are
  650-1,250 tokens, so each is read in one slice.

## Next levers for prompt reading

With the experts fast, the VM profile (`perf`, pp512) puts the dense layers first: the repacked
Q5_K and Q6_K GEMMs are 49% of prompt time, the expert kernels about 25%, the gated DeltaNet 5%.
ik_llama.cpp does the dense layers about 22% faster (it converts Q5_K to an interleaved 8-bit
layout as it does for the experts), worth about 10% more prompt speed if ported; it would replace
llama.cpp's repack for those tensors, which also serves generation. On the sources-first route the
search (about 11 s) is now a larger share of a question.
